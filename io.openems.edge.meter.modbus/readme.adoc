= Generic Modbus Meter

Reads an active power and cumulative active energy values from arbitrary
registers on an arbitrary Modbus device, and exposes them as a standard
`ElectricityMeter`.

There is no device-specific code in this bundle. Register type, register
address, encoding, word order and scale factor are all component configuration,
so supporting a new installation is a configuration change rather than a
firmware release. This matters for bespoke energy management systems, where the
register map differs per site even when the hardware and the vendor do not.

== Configuration

Each instance reads one meter. Add one instance per meter; several instances
may share a Modbus bridge and a unit-id.

Power, energy and reverse energy are configured independently, each with the
same set of `*RegisterType`, `*Address`, `*Encoding`, `*WordOrder` and
`*ScaleFactor` properties:

* `...RegisterType` -- `HOLDING_REGISTERS` (Modbus function code 3) or
  `INPUT_REGISTERS` (function code 4). Named after the register kind because
  that is the word vendor documentation uses.
* `...Encoding` -- `INT16`, `UINT16`, `INT32`, `UINT32` or `FLOAT32`.
* `...WordOrder` -- which half of a 32-bit value sits at the configured
  address. `HIGH_WORD_FIRST` is the Modbus default; pick `LOW_WORD_FIRST` where
  the documentation lists a `_low` register before its `_high` counterpart.
  Word order is a property of the value, not of the device, so it may differ
  within one meter -- the WP Friedhofallee controller really does mix them.
* `...ScaleFactor` -- what the register value is multiplied by to reach the
  channel unit, chosen from `ONE_THOUSANDTH`, `ONE_HUNDREDTH`, `ONE_TENTH`,
  `ONE`, `TEN`, `HUNDRED`, `THOUSAND`. Power targets Watt, so a register in W
  uses `ONE` and in kW uses `THOUSAND`. Energy targets Watt-hours, so a
  register in Wh uses `ONE`, in 1/10 kWh uses `HUNDRED` and in kWh uses
  `THOUSAND`.
* `powerInvert` -- negates the active power to correct a reversed measurement
  convention. It does not affect energy registers. With `energySource`
  `INTEGRATE_FROM_POWER`, the integrated energy follows the inverted power.

`powerSource` is `READ_FROM_REGISTER` (the default) or `NOT_AVAILABLE`, for
devices that only expose energy counters. Without power, `energySource` must be
`READ_FROM_REGISTER`. A `GRID` meter without power leaves
`_sum/GridActivePower` undefined, so controllers that act on grid power will not
work on that site.

=== Energy direction

Energy follows the OpenEMS `ElectricityMeter` convention for every meter type:
`ActiveProductionEnergy` accumulates positive active power,
`ActiveConsumptionEnergy` negative active power. What "positive" means depends
on the `type`:

[cols="1,2,2"]
|===
| `type` | `energy...` -> `ActiveProductionEnergy` | `reverseEnergy...` -> `ActiveConsumptionEnergy`
| `GRID`, `GRID_GENSET` | buy-from-grid | sell-to-grid
| `PRODUCTION` | production | (rarely available)
| `PRODUCTION_AND_CONSUMPTION` | production | consumption (commonly available)
| `CONSUMPTION_METERED`, `MANAGED_CONSUMPTION_METERED`, `CONSUMPTION_NOT_METERED` | consumption | (rarely available)
|===

The reverse energy register is optional (`reverseEnergyEnabled`, off by
default). Enable it when the device has a second counter for the opposite
direction, as most grid meters do.

`energySource` selects where the energy values come from:

[cols="1,4"]
|===
| `READ_FROM_REGISTER` | Read the energy register, and the reverse energy register if enabled. The default.
| `INTEGRATE_FROM_POWER` | Integrate the active power over time, for devices that expose no energy register. Positive power counts into `ActiveProductionEnergy`, negative power into `ActiveConsumptionEnergy`, so neither counter runs backwards.
| `NOT_AVAILABLE` | Power only; the energy channels stay undefined.
|===

The three are mutually exclusive by construction. Reading an energy register
and integrating power into the same channel would double-count.

== Upgrading

Earlier versions wrote the energy to `ActiveConsumptionEnergy`. Existing
instances now write it to `ActiveProductionEnergy` instead, and OpenEMS's local
history of the old channel stops. The matching ROOCKiE gateway release reads the
new channel, the earlier ones the old. Ship this bundle and that gateway release
together; either one alone leaves consumption energy empty.

Instances with `energySource` `INTEGRATE_FROM_POWER` restart their counter at 0.
The new channel has no Timedata history to continue from. Their
`ActiveConsumptionEnergy` keeps its old total and from then on only grows while
the active power is negative.

== Modbus traffic

All configured values are read by a single Modbus transaction when they share a
register type and fit within 8 registers, which is the usual case. Otherwise
they are split into several.

At the default `priority` of `LOW`, the bridge executes one low-priority read
per cycle across all components, so bus load does not grow with the number of
configured meters; refresh latency does. Twelve meters on a 1 s cycle refresh
every ~12 s, which is ample for energy monitoring and matters where the
Modbus/TCP endpoint fronts a serial segment. Raise individual meters to `HIGH`
where finer resolution is needed; each one adds a transaction per cycle.

== Thermal meters

Heat meters (Wärmezähler) report W and Wh like everything else and are read the
same way. OpenEMS has no heat-meter nature, so they are indistinguishable from
electricity meters at the channel level -- use the `alias` to identify them, or
they will be counted as electricity consumption downstream.
